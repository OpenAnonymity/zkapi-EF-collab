# zkAPI v2 protocol design

zkAPI sells metered API access without requiring the API operator to learn
which on-chain deposit is paying for a request. Version 2 keeps the original
state-anchor/nullifier design, but uses a compact Groth16 proof over BN254 and
proof-friendly Schnorr signatures over Baby-JubJub.

## Why a proof exists

The original project plan does not require a STARK. It does require the client
to convince the server, without revealing the note, that all of the following
are true:

- the client knows the secret for a leaf in the active deposit tree;
- the private balance is at least the deployment's charge bound;
- the note has not expired;
- the nullifier belongs to the current private state anchor;
- after the first request, the current balance commitment and anchor were
  authorized by the server;
- the proof authorizes this exact client request ID and payload digest.

Sending these witnesses in plaintext would link requests to a deposit and leak
the balance. A signature alone cannot prove the private Merkle-membership,
balance, and expiry predicates. Therefore a zero-knowledge proof is useful, but
the proof system does not need to be a STARK. Stwo-Cairo was an implementation
choice whose prover startup, trace construction, and memory use were a poor fit
for a per-chat client operation.

## Chosen construction

Each request carries a circuit-specific Groth16 proof on BN254. The serialized
proof is eight uncompressed base-field coordinates (256 bytes) so it can be
decoded directly by Solidity's BN254 precompiles. The HTTP wire form base64
encodes those bytes.

The circuit has 12 public field elements:

1. protocol version
2. chain ID
3. vault address
4. active Merkle root
5. state-signing public key x
6. state-signing public key y
7. request timestamp
8. solvency bound
9. request nullifier
10. authorization tag
11. anonymous balance-commitment x
12. anonymous balance-commitment y

The note ID, deposit amount, expiry, Merkle path, current balance, commitment
blinding, state anchor, request context, and state signature remain private.
The authorization tag is Poseidon(nullifier, request context); the request
context commits to the exact client request ID and canonical payload digest.

Withdrawal proofs use 14 public fields and additionally bind the destination,
final balance, clearance mode, and deployment-pinned clearance key. Mutual
close requires a server clearance signature. Escape close omits clearance and
uses the on-chain challenge period.

## State transitions

The client holds a private Pedersen balance commitment `C = balance*G + r*H`.
Before a request, it rerandomizes the commitment. After executing the upstream
request, the server homomorphically subtracts the charge, adds fresh blinding,
derives the next anchor, and signs the next state. This makes sequential
requests possible without revealing the balance or linking the anonymous
commitment to the deposit.

The server stores nullifiers and finalized transcripts for replay prevention,
idempotent retries, and crash recovery. It verifies the proof before invoking
the paid upstream provider.

## On-chain verification

`Groth16ProofAdapter` contains the selected request and withdrawal verification
keys and invokes the EIP-196/EIP-197 BN254 precompiles. `ZkApiVault` pins that
adapter and both server public keys at construction. The adapter is immutable;
an owner cannot swap in a permissive verifier after users deposit.

The vault and circuits use the same generated Poseidon parameters. Foundry
tests verify Rust-generated request and withdrawal proofs and reject tampered
public inputs. The active-note Merkle tree is depth 32. Expiry is rounded up to
a one-day bucket at deposit, avoiding needlessly precise public timing metadata.

## Setup and security status

Groth16 needs a circuit-specific structured reference string. The exact v2
proving keys, verification keys, manifest, and generated Solidity sources are
versioned under `protocol/setup/v2`; clients must use those files for the
deployed verifier. Running `zkapi setup` creates a different setup and is only
appropriate when intentionally creating a fresh deployment.

The current setup was generated by one party, not a multi-party ceremony, and
the implementation has not been audited. Arkworks also labels its Groth16 crate
as an academic proof-of-concept. This is suitable for the public public testnet demo,
not production funds. A production launch needs an audited implementation,
reproducible parameter-generation process, and multi-party setup ceremony (or a
different proof system with an acceptable setup model).

## Performance target

On the development machine, standalone release-mode request proving is roughly
0.35 seconds, verification is roughly 2 milliseconds, and peak proving memory
is roughly 184 MB. Exact results vary by CPU. This is orders of magnitude less
work than starting the Stwo-Cairo toolchain for every chat request, while still
proving the private predicates the protocol actually needs.
